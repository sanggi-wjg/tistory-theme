# 배포 후 프로덕션 검증

`/skin-qa-check`는 **소스가 맞는가**를 본다. 이 스킬은 **라이브가 맞는가**를 본다.

둘은 다른 일이다. 이 프로젝트는 배포가 스킨 편집기 **수동 복붙**이라(`DECISIONS.md` #15) 소스와 프로덕션이 갈라질 경로가 여럿 있다.

| 소스는 맞는데 프로덕션이 틀리는 경로 | 소스 린트가 잡는가 |
|---|---|
| 에디터에 붙여넣다 마크업이 잘렸다 | ✗ |
| `script.js`를 파일업로드에 안 올렸다 | ✗ |
| CSS 탭만 저장하고 적용을 안 눌렀다 | ✗ |
| `index.xml`을 올려 스킨 설정이 초기화됐다 | ✗ |
| 모바일웹 자동 연결이 켜져 있어 크롤러가 다른 페이지를 본다 | ✗ |

전부 **화면은 멀쩡해 보이는데 유입만 사라지는** 종류다.

## 실행

```bash
python3 .claude/skills/seo-verify-live/scripts/verify.py --base https://sanggi-jayg.tistory.com
```

오류가 있으면 exit code 1.

| 플래그 | 용도 |
|---|---|
| `--save-baseline` | 현재 지표를 `data/seo-baseline.json`에 기준선으로 저장 |
| `--compare` | 직전 baseline과 비교해 **회귀**를 잡는다 |
| `--allow-missing` | 원래 없는 페이지 타입(방명록을 껐다든가)을 빼고 저장 |
| `--json` | 자동화용 |

**배포 전에 `--save-baseline`, 배포 후에 `--compare`.** 이 순서가 이 스킬의 핵심이다 — 절대값보다 "배포로 무엇이 줄었는가"가 훨씬 잘 잡힌다.

**`--save-baseline`은 검사 오류가 있어도 baseline을 남긴다.** 배포 전 라이브는 이전 스킨이므로 `V003`·`V009`·`V010`이 뜨는 게 정상이다. exit code 1을 보고 멈추지 마라 — 이 명령은 게이트가 아니라 기록이다.

**단 `V014`는 다르다.** 8개 페이지 중 하나라도 못 받았거나, 기존 baseline에 있던 페이지가 빠지거나, 다른 블로그의 기준선을 덮으려 하면 **저장을 거부한다** — 전부 아니면 전무다.

그 페이지 타입이 **원래 없는 것**이면(방명록을 껐다든가) `--allow-missing`으로 명시하고 진행한다. 빠진 것은 baseline의 `missing`에 남고, 회귀 감시에서 제외된다. 불완전한 기준선으로 덮으면 배포 후 `--compare`가 비교할 것이 없어 **오류 없이 통과한다** — 회귀 게이트가 정확히 필요한 순간에 조용히 사라진다. `V014`가 뜨면 원인을 고치고 다시 찍어라.

```bash
# 배포 직전 (현재 라이브 = 이전 스킨)
python3 .claude/skills/seo-verify-live/scripts/verify.py --base https://... --save-baseline

# ... 사용자가 스킨 편집기에서 배포 ...

# 배포 직후
python3 .claude/skills/seo-verify-live/scripts/verify.py --base https://... --compare
```

## 검사 항목

| 코드 | 검사 | 실패 시 의미 |
|---|---|---|
| `V001` | 8개 페이지 타입 HTTP 200 | 그 URL이 죽었다 |
| `V002` | **미치환 치환자 잔존** (`[##_..._##]`, `<s_...>`) — `<pre>`·`<code>`·주석 제외 | 티스토리가 해석 못 한 것. 글 페이지는 오류, 목록은 경고(요약문은 마크업이 걷힌 평문이라 인용을 못 가린다) |
| `V003` | `h1` 페이지당 정확히 1개 | 0개면 크롤러가 주제를 모르고, 2개 이상이면 주제가 갈린다 · **홈의 h1 0개는 경고다** — 의도된 예외(DESIGN.md §3) |
| `V004` | `<html lang>` | 스크린리더·검색엔진 언어 판단 |
| `V005` | `canonical` 존재 | 티스토리가 넣던 것이 사라졌다면 `<head>`가 깨졌다 |
| `V006` | **글 페이지의 다른 글 링크 수**와 주소 형태 | 0이면 관련글·이전/다음이 렌더되지 않았다. **자기 자신은 세지 않는다** — 글은 제목·공유 링크로 자기를 2번 링크한다. 전부 `/{번호}`면 비정규 주소를 향한다 |
| `V007` | JSON-LD 파싱 + `BlogPosting` + 글 페이지 `BreadcrumbList` | 치환자가 따옴표를 깨뜨리면 통째로 무효가 된다 |
| `V008` | 본문 이미지 `alt` 커버리지 | **콘텐츠 이슈** — 보고만 한다 |
| `V009` | **라이브 `style.css` ↔ `dist/style.css` 대조** | 붙여넣기가 잘렸거나 반영이 안 됐다 |
| `V010` | **모바일 우선 색인 동등성** — PC가 건 스킨 CSS와 대조 | 아래 참조 |
| `V011` | `robots.txt` · `sitemap.xml` 생존 | 티스토리 소관이지만 죽으면 유입이 죽는다 |
| `V012` | baseline 회귀 (`--compare`) | 구조화 데이터 유실·페이지 실종. 내부링크 감소는 **글 페이지만 오류** — 목록의 링크 수는 글이 몇 편 실렸는가라 콘텐츠에 딸린 값이다 |
| `V013` | 목록 2페이지의 `canonical` | 루트로 접히면 2페이지 이후가 독립 색인되지 않는다 |
| `V014` | baseline 저장 안전장치 (`--save-baseline`) | 불완전한 기준선·다른 블로그 기준선이 좋은 기준선을 덮는 것을 막는다 |
| `V015` | 입력 JSON 읽기 실패 | `data/posts.json`·baseline이 깨져도 리포트를 잃지 않는다 |

## 구조화 데이터 — 티스토리가 어디에 무엇을 넣는가

2026-08-25 실측. **페이지 타입마다 다르다.**

| 페이지 | 티스토리가 주입하는 JSON-LD |
|---|---|
| 홈 · 보관함 · 태그 · 검색 · 방명록 | `WebSite` |
| 글 | `BlogPosting` — **빵부스러기 없음** |
| 카테고리 | `BreadcrumbList` |

**글 페이지에만 `BreadcrumbList`가 없다.** 카테고리 계층이 상위 14 / 하위 21로 정리된 블로그이므로(`DECISIONS.md` 결정 27) 글에서 빵부스러기가 빠지는 것은 아까운 자리다. 스킨이 채울 수 있고, `V007`이 그 자리를 비워 뒀는지 알려 준다. **필수는 아니다** — 없다고 오류를 내지 않는다.

## `V010` — 이 블로그의 최대 리스크

구글은 **모바일 우선 색인**이다. 모바일웹 자동 연결이 켜져 있으면 스마트폰 UA가 `/m/`으로 302되고, 거기서는 커스텀 스킨이 로드되지 않는다.

2026-08-25 실측 (같은 글, PC와 `/m/`):

| | PC | `/m/` — **구글이 보는 쪽** |
|---|---|---|
| `h1` | 2 | **0** |
| 다른 글로 가는 링크 | 15 | **0** |
| 카테고리 링크 | 37 | 1 |

`V010`이 오류를 내면 **스킨 코드로는 고칠 수 없다.** 관리 → 꾸미기 → 모바일 → 모바일웹 자동 연결을 꺼야 한다(`DECISIONS.md` 결정 2). 리포트에서 **사용자 조치 항목**으로 따로 뽑아 올린다 — 코드로 못 고치는 것이 다른 지적에 묻히면 안 된다.

## 티스토리 고유 사실 — 검사를 읽을 때 알아야 할 것

- **글 주소가 두 형태다.** `/entry/{제목}`과 `/{번호}`가 모두 200이고 `canonical`은 항상 문자 형태다. 스크립트는 둘 다 내부링크로 센다 — 한 형태만 세면 주소 설정 하나로 "내부링크 0" 오경보가 난다
- **목록 2페이지의 `canonical`이 루트로 접힌다.** `V013`이 알려 준다. 티스토리 소관이라 못 고치지만, 페이징을 크롤 경로로 믿으면 안 된다는 뜻이다
- **`og:image`는 스킨이 못 바꾼다.** 대표이미지 없는 글은 티스토리 기본 이미지가 나간다. 카테고리 기본이미지(CSS 배경)로는 해결되지 않는다

## 어느 블로그를 검증하는가

`DECISIONS.md` #22에 따라 **개발은 테스트 블로그에서** 한다. `--base`를 반드시 명시적으로 넘기고, **리포트 첫 줄에 검증한 URL을 적는다.** 테스트 블로그 결과를 본 블로그 결과로 착각하면 배포 사고가 그대로 남는다.

## 리포트 규칙

`_workspace/seo-report.md`에 **통과 / 실패 / 미검증** 3분류. `/skin-qa-check`와 같은 규칙이다.

**네트워크 실패는 "실패"가 아니라 "미검증"이다.** 스크립트도 `❔`로 따로 표시한다 — 차단·점검을 스킨 결함으로 적으면 다음 사람이 잘못된 곳을 판다.

## 일부러 검사하지 않는 것

오탐이 실제로 나기 때문에 범위를 좁힌 자리들이다. **이 블로그가 개발 블로그라서** 생기는 문제다.

| 자리 | 왜 뺐나 |
|---|---|
| `<pre>` · `<code>` 안 | 글에서 티스토리 치환자를 예시로 인용한다 |
| `<head>`의 `meta`·JSON-LD | 티스토리가 **본문 평문**으로 만들므로 위 인용이 그대로 들어온다 |
| `<title>` | 티스토리가 글 제목을 그대로 넣는다. 제목에 치환자를 쓴 글이 곧 오탐이 된다 |
| HTML 주석 | 주석 처리해 둔 `<h1>`·`<a>`·`<img>`는 렌더되지 않는다 |

**따라서 `<head>`에 남은 미치환 치환자는 `V002`가 잡지 못한다.** 대신 `V003`(`h1`)·`V005`(`canonical`)·`V007`(JSON-LD)이 `<head>`가 깨졌는지를 다른 각도에서 본다.

## 이 스킬이 못 잡는 것

정적 HTML만 본다. 다음은 여전히 육안·외부 도구가 필요하다.

- **실제 검색 순위와 유입** — GSC/네이버 서치어드바이저를 봐야 한다. 이 스킬은 "크롤러가 받아 갈 HTML이 맞는가"까지다
- **JS 렌더링 후 DOM** — 목차·다크모드 토글이 만드는 DOM은 응답 HTML에 없다. 크롤러도 대부분 못 보므로 **거기에 SEO를 의존하면 안 된다**는 뜻이기도 하다
- **Core Web Vitals 실측** — LCP·CLS는 PageSpeed Insights나 GSC의 CWV 리포트
- **색인 여부** — `site:` 검색이나 GSC의 URL 검사
