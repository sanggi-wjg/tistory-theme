# PR 리뷰 게이트

`gh pr create` 앞에 서는 마지막 검사다. **`npm run check`와 보는 축이 다르다.**

| | `npm run check` | 이 게이트 |
|---|---|---|
| 무엇을 보나 | 규칙이 **있는가** | 그 규칙이 이 변경에서 **실제 조건을 재현하는가** |
| 방식 | 결정적 — 스크립트가 판정 | 판단 — diff를 읽고 근거로 판정 |
| 놓치는 것 | 규칙 자체가 틀렸을 때 | 규칙으로 표현되는 것 |

**이 게이트가 존재하는 이유는 저장소에 이미 적혀 있다.** CLAUDE.md —
"검증 도구가 통과 신호를 위조한 적이 세 번 있다." 셋 다 린트와 프리뷰가
초록불을 켰고, 실제 배포에서만 드러났다. **린트가 통과했다는 사실은
이 게이트의 입력이지 결론이 아니다.**

## 실행

### 0. 전제 확인

```bash
git rev-parse --abbrev-ref HEAD          # main이면 여기서 멈춘다
git status --porcelain                    # 비어 있어야 한다
git --no-pager diff --stat main...HEAD
```

- **`main`이면 중단한다.** 리뷰할 브랜치가 없다.
- **작업 트리가 더러우면 중단한다.** 커밋되지 않은 변경은 PR에 안 들어간다 —
  리뷰한 것과 올라가는 것이 달라진다.
- diff가 비어 있으면 중단한다.

### 1. 변경 전체를 읽는다

```bash
git --no-pager diff main...HEAD
git --no-pager log main..HEAD --oneline
```

**`diff --stat`만 보고 판정하지 않는다.** 이 도메인의 결함은 한 줄짜리다 —
선택자 한 글자, 치환자 이름 하나, 특이도 한 칸.

### 2. 다섯 축으로 본다

각 축의 지적은 **파일:라인 + 무엇이 어떻게 어긋나는가 + 근거**로 쓴다.
"스타일이 안 먹을 것 같다"는 지적이 아니다.

축별 상세 점검표는 `references/review-axes.md`에 있다. **처음 읽는다면 먼저 그 파일을 읽어라.**

| # | 축 | 한 줄 |
|---|---|---|
| 1 | **상위 규범 충돌** | `DECISIONS.md` 결정·`DESIGN.md` 토큰과 부딪히는가. 부딪혔다면 문서를 **먼저** 고쳤는가 |
| 2 | **조용히 실패하는 결함** | 특이도, 셀렉터 불일치, 치환자, 테마 한쪽만 깨지는 것 |
| 3 | **검사가 이 변경을 볼 수 있는가** | 린트·프리뷰가 통과했다면, 그 검사가 이 변경의 실패 모드를 **재현하는가** |
| 4 | **문서 동기화** | 코드가 바뀐 만큼 `DECISIONS.md`·`DESIGN.md`·`docs/hooks.md`·`TODO.md`가 따라왔는가 |
| 5 | **일반 코드 품질** | 정확성·중복·불필요한 복잡도 |

**5번은 빌트인 `/code-review`에 위임한다.** 같은 것을 두 번 하지 않는다.
1~4번은 이 저장소에만 있는 축이라 위임할 곳이 없다.

### 3. PR 본문 요건을 확인한다

CLAUDE.md가 PR 본문에 요구하는 네 가지가 준비되어 있는가.

- **무엇을** 바꿨는가 — 파일 나열이 아니라 결과로
- **왜** — `DECISIONS.md` 결정 번호 / `DESIGN.md` 절 참조
- **어떻게 확인했는가** — 린트 결과, 프리뷰에서 본 페이지
- **검증하지 못한 것** — 이 항목이 비어 있으면 **의심한다.** 이 도메인에서
  "전부 확인했다"가 참인 경우는 드물다. 라이브는 배포 후에만 볼 수 있다

`_workspace/qa-report.md`가 있으면 그 "미검증" 항목이 PR 본문으로 옮겨졌는지 본다.

### 4. 판정하고 기록한다

`_workspace/pr-review.md`에 쓴다. 항목마다 **차단 / 경고 / 통과** 셋 중 하나다.

| 판정 | 뜻 | 다음 |
|---|---|---|
| **차단** | 이대로 머지되면 깨진다 | 고치고 커밋한 뒤 이 스킬을 **다시** 실행 |
| **경고** | 깨지지는 않지만 남는 빚 | PR 본문에 적고 진행 |
| **통과** | 확인했고 문제없다 | — |

**"미검증"을 "통과"로 적지 않는다.** 못 본 것은 못 봤다고 쓰고 경고로 올린다.

### 5. 차단이 0일 때만 마커를 찍는다

```bash
git rev-parse HEAD > .claude/.pr-review-ok
```

이 한 줄이 `gh pr create`를 열어 준다(`.claude/hooks/pr-review-gate.py`).

**차단 항목이 남아 있는데 찍지 마라.** 찍는 순간 "이 커밋을 읽었고 문제가 없다"는
뜻이 되고, 그 문장이 거짓이면 게이트는 있는 것이 없는 것보다 나쁘다 —
다음 사람이 초록불을 믿는다. 이 저장소가 위조된 통과 신호로 세 번 데인 이유다.

**사용자가 명시적으로 건너뛰라고 하면** 그대로 따르되, 마커를 찍지 말고
`gh pr create`가 막히는 것을 사용자에게 알린 뒤 지시를 받는다.

## 게이트 자체가 위조될 수 있는 자리

이 게이트도 검사다. 검사는 위조된 신호를 낸다.

- **마커는 커밋 SHA 하나다.** 리뷰 뒤에 커밋을 더 쌓으면 훅이 다시 막는다 —
  그때 "리뷰는 이미 했으니까"라며 마커를 다시 찍는 것이 가장 흔한 위조 경로다.
  **새 커밋이 무엇을 바꿨는지 보고 나서** 찍는다. 오타 수정이면 몇 초면 된다.
- **탐지기는 완벽하지 않다.** `.claude/hooks/test-detect.py`가 14케이스를 지키고
  `npm run check`가 그것을 돌린다. 첫 판이 명령문 안의 **문자열**을 잡았고,
  둘째 판이 `VAR=x gh …` 형태를 **놓쳤다** — 두 번 다 케이스를 먼저 추가하고 고쳤다.
  탐지기를 손대면 그 순서를 지킨다. 알려진 한계는 훅 파일 상단에 적혀 있다.
- **훅은 PR 생성 명령만 본다.** 웹 UI로 PR을 열면 게이트를 지나지 않는다.
  그건 사용자의 선택이고 도구가 막을 수 있는 것이 아니다.
- **`npm run check` 통과는 이 리뷰의 입력이다.** 초록불을 근거로 축 3을
  건너뛰면 게이트가 하는 일이 없어진다.

## 테스트 시나리오

### 정상 흐름
1. 사용자: "PR 올려줘" (브랜치에 커밋 3개, `npm run check` 통과)
2. 0단계 — 브랜치 확인, 트리 깨끗, diff 8파일
3. 1~2단계 — diff 전체 정독, 축 1에서 `DESIGN.md §5.3`과 부딪히는 CSS 발견 →
   문서가 같은 커밋에서 갱신됐는지 확인 → 갱신됨, **통과**
4. 축 3 — 새 JS 모듈이 프리뷰에서 실제로 실행되는지 확인 → 확인 못 함, **경고**
5. 3단계 — PR 본문 4요건 중 "검증하지 못한 것"이 비어 있음 → 축 4의 경고를 넣도록 지시
6. 차단 0 → 마커 기록 → `gh pr create` 통과

### 에러 흐름
1. 축 2에서 `.contents_style a`(0,1,1)를 이기지 못하는 새 규칙 발견 → **차단**
2. 마커를 찍지 않고 사용자에게 보고
3. 담당 에이전트(또는 직접)가 수정 → 커밋 → `npm run check`
4. 이 스킬을 **다시** 실행 → HEAD가 바뀌었으므로 새 커밋을 포함해 재판정
5. 차단 0 → 마커 → PR

### 게이트 오작동 흐름
1. `gh pr create`가 막혔는데 리뷰를 방금 끝냈다
2. 훅 메시지의 SHA 두 개를 비교한다 — 리뷰 뒤에 커밋이 쌓였는지, 마커가 없는지
3. 커밋이 쌓였으면 **그 커밋만** 리뷰하고 마커를 다시 찍는다
4. 마커가 아예 없는데 리뷰를 했다면 5단계를 빠뜨린 것이다
