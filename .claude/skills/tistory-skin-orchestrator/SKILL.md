# 티스토리 스킨 오케스트레이터

`sanggi-jayg.tistory.com` 커스텀 스킨을 만드는 팀을 조율한다.

## 실행 모드

| Phase | 실행 모드 |
|---|---|
| Phase 1 (실측, 필요 시) | 서브 에이전트 — 결과만 한 번 받는다 |
| Phase 3 (구현) | **이름 있는 팀원** — `Agent(name:)`로 띄우고 `SendMessage`로 다시 깨운다. 마크업↔CSS↔JS가 훅으로 얽혀 있어 고치고 다시 보는 왕복이 품질을 좌우한다 |
| Phase 4 (마지막 체크포인트) | skin-qa — 리더가 연다. 빌드·린트·프리뷰는 한 번에 한 곳에서만 돈다 |

**`TeamCreate`·`TeamDelete`는 없다. 에이전트 팀은 형태가 바뀌어 남아 있다.** `Agent(name: "…")`로 띄운
에이전트가 곧 팀원이고(`in_process_teammate`), 팀은 따로 만들지 않으며 리더는 `team-lead`로 잡힌다.
이 동작을 켜는 것이 `.claude/settings.json`의 `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`이다(공식 문서 agent-teams
기준 — 꺼서 시험하지는 않았다). **지우면 Phase 3의 전제가 꺼진다.** 예전 판은 `TeamCreate` 유무로 갈라서, 팀원 기능이 있어도
매번 한 번 돌고 끝나는 파이프라인으로 내려갔다.

2026-10-05 점검(Claude Code 2.1.289, 대화형 CLI)에서 실측한 것:

- 유휴가 된 팀원을 `SendMessage`로 깨우면 **맥락을 유지한 채** 이어간다
- 팀원끼리 직접 보낼 수 있고, 그 요약이 리더의 유휴 알림에 실려 온다. 단 팀원에게 `SendMessage`는
  **지연 도구**라 `ToolSearch("select:SendMessage")`로 불러와야 보인다 — 모르면 "통보할 수단이 없다"고 결론 낸다
- 공유 작업 목록(`TaskCreate`·`TaskUpdate`·`TaskGet`)은 **올라오지 않았다**(문서에는 있다). 작업표는 리더가 들고 간다
- 리더에게도 `SendMessage`·`TaskStop`은 지연 도구였다 — 처음 쓰기 전에 `ToolSearch`로 불러온다.
  `ListAgents`는 다른 세션만 보여 주고 **팀원은 보여 주지 않는다**
- 팀원을 멈추는 것은 `TaskStop`(이름으로). **멈춘 팀원도 이름으로 보내면 맥락째 다시 깨어난다.** 같은 이름으로
  새로 띄우면 이후 그 이름으로 온 메시지는 새 쪽으로 간다(나중 것이 이름을 가져간다)

**설정이 아니라 도구 목록이 사실이다.** 위는 그날의 실측이다. 플래그가 꺼졌거나 환경이 다르면 팀원으로 뜨지
않을 수 있다. 환경을 미리 판정하지 않는다 — 띄운 결과를 보고 §에러 핸들링 「팀원으로 뜨지 않는다」로 내려간다.
체크포인트는 리더가 쥐므로 어느 쪽이든 검증이 빠지지 않는다.

## 팀 구성

| 팀원 | 타입 | 역할 | 주 스킬 | 출력 |
|---|---|---|---|---|
| `skin-markup` | 커스텀 | `skin.html` · `index.xml` | `/tistory-substitutions` | `src/skin.html`, `src/index.xml`, `docs/hooks.md` |
| `skin-style` | 커스텀 | `style.css` | `/tistory-substitutions` | `src/styles/*.css` |
| `skin-behavior` | 커스텀 | `script.js` | — | `src/js/*.js` |
| `skin-qa` | 커스텀 | 검증 | `/skin-qa-check`, `/skin-preview` | `_workspace/qa-report.md` |
| `blog-analyst` | 커스텀 (서브) | 실측 | `/blog-census` | `data/*.json` |
| `seo-auditor` | 커스텀 (서브) | 검색엔진에 보이는 것 | `/seo-verify-live`, `/skin-qa-check` | `_workspace/seo-report.md`, `data/seo-baseline.json` |

**모델은 각 에이전트 정의의 frontmatter(`model:`)가 정본이다. 호출에서 `model`을 넘기지 않는다.**
호출 인자가 frontmatter보다 우선하므로, 넘기면 정의를 바꿔도 조용히 적용되지 않는다 — 두 곳에 적힌 값이 갈라지는 부류다.

## Phase 0: 컨텍스트 확인

0. **브랜치를 먼저 딴다** (`CLAUDE.md` 작업 방식) — `git switch main && git pull` 로 기점을
   맞춘 뒤 `git switch -c <작업 범위>` (`home-grid`, `toc-scrollspy`). `main`에서 작업하지
   않는다. 이미 작업 브랜치 위면 그대로 이어간다.
1. `_workspace/` 존재 여부 확인
2. 실행 모드 결정:
   - **미존재** → 초기 실행. Phase 1로
   - **존재 + 부분 수정 요청** ("카드만 다시", "목차 고쳐줘") → **부분 재실행.** 해당 에이전트만 호출하고 이전 산출물 경로를 프롬프트에 포함해 읽고 고치게 한다
   - **존재 + 새 방향 지시** → **새 실행.** `_workspace/`를 `_workspace_{YYYYMMDD_HHMMSS}/`로 옮기고 Phase 1로
3. `DECISIONS.md`와 `DESIGN.md`를 읽는다. **이 둘이 상위 규범이다.** 요청이 문서와 충돌하면 사용자에게 확인한다

## Phase 3: 구현 — 이름 있는 팀원

**실행 모드:** 이름 있는 팀원. 리더가 허브다. 생산 팀원(markup·style·behavior)은 병렬로 고치고, **검증은 생산
팀원이 모두 유휴일 때 리더가 체크포인트로 연다.** 빌드·린트·프리뷰는 한 번에 한 곳에서만 돈다 — 팀원이 떠 있는
동안은 skin-qa만, 아무도 일하지 않을 때만 리더. 산출물이 깨지는 것은 이제 장치가 막는다(이슈 #100) — `build.mjs`와
`render.py`가 잠금(`.dist.lock`·`.preview.lock`)으로 줄을 서고 파일마다 원자 교체하므로, 겹쳐 돌아도 서로 지우거나
잘린 파일을 읽지 않는다(`npm run test:build-lock`). 그래도 한 곳에서만 돌리는 이유는 **결과가 무엇을 검증했는지**다 —
검증 도중 생산 팀원이 소스를 바꾸면 초록불이 어느 판의 것인지 모른다. **「모두 유휴」는 리더의 판단이지 잠금이
아니다** — 생산 팀원끼리 보낸 메시지가 뒤늦게 누군가를 깨울 수 있다. 그래서 qa가 검증 앞뒤로 diff 지문을 비교한다(아래).

### 검사 절차 — 기준선과 체크포인트가 같이 쓴다

`npm run check`는 `&&` 사슬이라 **첫 실패에서 멈춘다** — 린트 오류 하나에 프리뷰는 옛 것으로 남고, 뒤 단계의
오류는 목록에 안 나온다. 그래서 사슬을 **기계로** 끊어 전부 돌린다 — 손으로 옮겨 적으면 단계가 빠진다:

```bash
node -p 'require("./package.json").scripts.check.split("&&").map(s=>s.trim()).join("\n")' \
  | while IFS= read -r c; do printf '== %s → ' "$c"; sh -c "$c" >/dev/null 2>&1 && echo ok || echo FAIL; done
```

`FAIL`이 난 단계만 따로 다시 돌려 내용을 본다. 빌드가 실패하면 `dist/`는 **통째로 지워진다** — `build.mjs`는 임시
폴더(`.dist.tmp-<pid>`)에 빌드해 성공했을 때만 옮기고, 용량 예산 초과를 포함해 실패하면 옛 산출물을 남기지 않으려고
`dist/`를 지운다. 그래서 뒤 단계의 `FAIL`은 대개 「`dist/`가 없다」는 같은 원인이다 — 뒤 단계 결과를 읽지 말고 빌드부터 고친다.
마지막 체크포인트는 `npm run check` 한 번이 통과해야 끝난다.

**diff 지문** — 검증 시작과 끝에 `{ git diff HEAD; git status --porcelain; } | shasum`을 적는다. 둘이 다르면 검증 중에
누군가 파일을 고친 것이다 — 그 체크포인트는 무효로 적고 리더에게 알린다.

### 기준선 — 아무도 일하지 않을 때

리더가 검사 절차를 돌려 남은 오류와 담당을 뽑는다. 처음이든 재진입(Phase 4 실패·게이트 차단·커밋 안 한 수정이
남은 브랜치)이든 같다. 커밋 전 검사는 규범일 뿐 훅이 강제하지 않으므로 트리가 통과 상태라고 가정하지 않는다.
남은 오류는 담당 팀원의 프롬프트(재진입이면 깨우는 메시지)에 넣는다.

### 띄우는 순서

```
skin-markup ── 작업 1(훅 계약)만 → 이름 목록 보고 → 유휴
      ↓ 리더가 이름 목록을 복사
한 메시지: skin-style · skin-behavior 띄움 + skin-markup 깨워 작업 3~5
      │  선행이 1이 아닌 작업(10 ← 5)은 그 선행이 끝났다는 보고를 받은 뒤 깨운다
      ↓ 생산 팀원이 모두 유휴
체크포인트 — skin-qa가 검사 절차 → 판정 → (경계면 이슈는 다 마친 뒤 양쪽에)
      ↓ 실패 → 담당을 같은 이름으로 깨워 고친다 → 모두 유휴 → 다시 체크포인트
Phase 4 — 마지막 체크포인트
```

**훅 계약이 먼저인 이유** — 작업 대부분이 계약의 이름을 읽는다(작업표 선행 열: `.entry-body`·`#theme-toggle`·
진행바까지). 계약보다 먼저 시작하면 이름이 어긋난 채 굳고, JS 셀렉터는 `null`을 돌려주고 끝난다. 계약은 짧으니
그것만 기다린다. 이번 요청에 훅을 건드리는 일이 없으면 작업 1을 건너뛰고 생산 팀원을 한 메시지에서 모두 띄운다.

```
Agent(name: "skin-markup", subagent_type: "skin-markup", description: "훅 계약 확정",
      prompt: "DECISIONS.md·DESIGN.md를 읽고 <요청 범위>에 필요한 훅 계약(docs/hooks.md)만 먼저 확정하라.
               새로 만들거나 바꾼 이름을 최종 보고 맨 앞에 목록으로 적고 끝내라. 마크업 반영은 다음 지시에서 한다.
               <담당 파일> <생산 팀원 공통 문구> 이 단계에서는 SendMessage를 쓰지 않는다 — 이름 목록은 최종 보고에만.")
```

markup의 보고를 받으면 **한 메시지에서**:

```
Agent(name: "skin-style", subagent_type: "skin-style", description: "CSS 구현",
      prompt: "<markup이 보고한 이름 목록을 그대로 붙인다> <작업> <담당 파일> <기준선 중 이 담당의 오류> <생산 팀원 공통 문구>")
Agent(name: "skin-behavior", subagent_type: "skin-behavior", description: "JS 구현", prompt: "… (같은 형식)")
SendMessage(to: "skin-markup", message: "작업 3~5를 진행하라: …")
```

체크포인트는 생산 팀원이 모두 유휴일 때 연다. 첫 번째는 띄우고, 그다음부터는 같은 이름으로 깨운다:

```
Agent(name: "skin-qa", subagent_type: "skin-qa", description: "체크포인트 검증",
      prompt: "<QA 문구> <n>차 체크포인트. 이번에 바뀐 것: <생산 팀원 보고 요약>")
SendMessage(to: "skin-qa", message: "<n>차 체크포인트. 이번에 바뀐 것: …")
```

**생산 팀원 공통 문구** — markup·style·behavior 프롬프트 끝에 그대로 붙인다:

> 다른 생산 팀원과 합의할 것(훅 이름, 생성 DOM 클래스)은 `SendMessage`로 보낸다. 지연 도구라 처음에는 목록에
> 없다 — `ToolSearch`(query: `"select:SendMessage"`)로 불러온다. 보낼 수 없으면 최종 보고에 적는다 — 리더가 중계한다.
> **빌드·린트·프리뷰는 어떤 형태로도 돌리지 않는다**(`npm run` 스크립트든 `build.mjs`·`lint.py`·`render.py`
> 직접 실행이든). skin-qa에게 직접 검증을 요청하지도 않는다 — 검증은 리더가 모두 멈춘 때 체크포인트로 연다.
> `dist/`와 무관한 단위 검사(`npm run test:code`)는 된다. 정의가 「프리뷰로 본다」고 한 확인(색·라이트박스 등)은 직접
> 하지 말고 「확인 못 함」에 적는다 — 체크포인트에서 qa가 본다. 끝나면 바꾼 것과 「확인 못 함」을 최종 보고에 적는다.

**QA 문구** — skin-qa 프롬프트에 그대로 붙인다:

> 리더가 연 체크포인트에서만 검증한다. 그때 생산 팀원은 모두 멈춰 있어야 한다. 시작과 끝에 diff 지문
> (`{ git diff HEAD; git status --porcelain; } | shasum`)을 적고, 다르면 이 체크포인트는 무효다. 아래 명령으로 `check`
> 사슬을 전부 돌린다(`npm run check`는 첫 실패에서 멈춰 프리뷰가 옛 것으로 남는다): <검사 절차의 명령을 그대로 붙인다>.
> 빌드가 실패했으면 뒤 단계를 믿지 말고 그것부터 보고한다. 프리뷰로 바뀐 영역과 「확인 못 함」에 적힌 것을 본다.
> 지적(경계면 이슈 포함)은 **검증을 다 마친 뒤에** 담당에게 `SendMessage`로 보낸다 — 경계면은 생산자·소비자 양쪽에
> (지연 도구 — `ToolSearch`(query: `"select:SendMessage"`)). 검증 중에 깨우면 고치는 파일을 검사하게 된다.
> 파일은 고치지 않는다 — 정의의 「명백한 오타」 예외도 이 흐름에서는 담당에게 보낸다.
> `_workspace/qa-report.md`에 `## <n>차 체크포인트 · <시각>` 절을 열고 **통과 / 실패 / 미검증 3분류**로 쓴다.
> **미검증을 통과로 적지 않는다** — 이 도메인은 조용히 실패하므로 "아마 될 것"이 가장 위험한 문장이다.
> 리더가 넘긴 「확인 못 함」은 미검증에 옮긴다. 렌더러 결함이면 고치지 말고 리더에게 보고한다(skin-qa 정의).

### 담당 파일 — 같은 작업 트리를 쓴다

생산 팀원은 같은 작업 트리를 동시에 고친다. 두 명이 같은 파일을 통째로 쓰면 한쪽이 덮인다. 아래 줄을 각 프롬프트의
`<담당 파일>` 자리에 복사하고 "다른 파일은 건드리지 마라 — 지금 다른 팀원이 고치고 있다"를 붙인다.

| 팀원 | 고칠 수 있는 것 |
|---|---|
| skin-markup | `src/skin.html`, `src/index.xml`, `docs/hooks.md` — 작업 1에서는 파일 전체(JS가 만들 클래스 이름도 계약에 미리 박는다). 그 뒤로는 자기가 만든 이름의 줄(`head-inline`이 거는 §8 상태 클래스 포함) |
| skin-style | `src/styles/*.css`, `DESIGN.md`(토큰에 없는 값이 필요할 때 — skin-style 정의의 규칙) |
| skin-behavior | `src/js/*.js`, `docs/hooks.md`에서 자기가 만든 이름의 줄(§5의 JS 계약, §5.6·§8의 JS 생성 클래스 — `BND006`·`BND007`이 읽는다). 다크모드 초기화 스니펫은 `src/skin.html`의 `head-inline` 블록이 정본 — 바꿀 때 skin-markup에게 교체를 요청 |
| skin-qa | `_workspace/qa-report.md` |

`docs/hooks.md`는 둘이 각자 만든 이름의 줄만 고친다 — **`Edit`로 그 줄만 고치고 `Write`로 통째로 쓰지 않는다.**

### 리더가 직접 지는 책임

- **훅 중계.** markup이 정한 이름을 style·behavior 프롬프트에 **그대로 복사해 넣는다.** 링크만 주지 마라
- **담당 파일을 못박는다.** 위 표를 프롬프트에 복사한다
- **체크포인트는 생산 팀원이 모두 유휴일 때만 연다.** 마지막 지시 뒤에 유휴 알림이 온 팀원만 유휴다(`ListAgents`는
  팀원을 보여 주지 않는다). 이것은 판단이지 잠금이 아니다 — qa의 diff 지문이 뒤를 받친다.
  팀원끼리 보낸 메시지의 요약도 유휴 알림에 실려 온다(2026-10-05에 한 건으로 확인) — 작업표는 그것으로 갱신한다
- **되돌릴 때는 같은 이름으로 깨운다.** `SendMessage(to: "skin-style", message: …)` — 새로 띄우면 앞서 읽은 맥락을 잃는다.
  qa가 검증을 마치고 담당에게 이미 보낸 지적은 다시 보내지 않는다 — qa-report로 확인만 한다(지시가 두 갈래가 된다)
- **「확인 못 함」을 모아 넘긴다.** 생산 팀원의 최종 보고에서 모아 다음 체크포인트 메시지에 넣는다. qa-report의 미검증 절과
  PR의 「검증하지 못한 것」으로 이어진다
- **협상이 길어지면 리더가 정한다.** behavior가 만드는 DOM 클래스는 훅 계약에 미리 박혀 있는 것이 가장 좋다. 빠졌는데
  합의가 한 번에 안 나면 리더가 정해서 양쪽에 같은 문장으로 전달한다. 같은 경계면 이슈가 2회 이상 반복되면 훅 계약 자체를
  재검토시킨다

## Phase 4: 마지막 체크포인트 — 빌드·프리뷰·검증

생산 팀원이 모두 유휴일 때 리더가 skin-qa에게 마지막 체크포인트를 연다.

1. `npm run check` 한 번이 통과한다 — 빌드·린트·테스트·프리뷰 12페이지. 실패하면 Phase 3의 체크포인트 고리로 돌아간다
   (최대 3회). `SEO001`(반복 블록 안의 `h1`)과 `SEO002`(내부링크 치환자 **전부** 누락)도 오류다 — 일부만 빠지면 경고다
2. **다크모드를 프리뷰에서 눈으로 본다.** 린트는 규칙의 **존재**만 확인한다. 티스토리 시트와의 특이도 싸움에서 실제로
   이기는지는 계산된 색을 봐야 안다 (DESIGN.md §5.2b). 프리뷰 하단에 주황색 경고 띠가 떠 있으면 티스토리 시트를 못
   불러온 것이니 이 확인은 무효다. 리더도 qa가 유휴일 때 `_preview/`를 열어 본다
3. `_workspace/qa-report.md` 최종본 확인 — **"미검증" 항목을 사용자에게 그대로 보고**

**`seo-auditor`는 여기서 팀원이 아니다.** Phase 3의 SEO 관심사는 `SEO001~005` 린트가 이미 덮으므로 팀을 5명으로 늘릴 이유가 없다. 이 에이전트는 **배포 전후**에 서브 에이전트로 부른다 — 배포 직전 `--save-baseline`, 배포 직후 `--compare`. 그때가 프로덕션 실물이 존재하는 유일한 시점이다.

## Phase 5: 정리

1. **팀원 정리.** `TaskStop`(이름)으로 모두 멈춘다 — 아래에서 리더가 `npm run check`를 돌리는 동안 다른 곳에서 빌드가
   돌면 안 된다. 멈춰도 이름으로 보내면 맥락째 다시 깨어나므로, 게이트 차단으로 Phase 3에 돌아가면 같은 이름으로 깨운다
2. `_workspace/` **보존** (사후 추적용)
3. `npm run check` 통과 확인 후 커밋. **린트 오류가 남은 채로 커밋하지 않는다**
4. 사용자에게 보고: 완료 항목 · 미검증 항목 · 배포 절차(`/skin-deploy`)
5. **`/pr-review-gate` — PR 리뷰.** 커밋 뒤, 푸시 전에 돈다.
   브랜치 전체 diff를 상위 규범 충돌·조용한 결함·**검사가 이 변경을 볼 수 있는가**·
   문서 동기화 네 축으로 읽고 차단/경고/통과를 판정한다. 일반 코드 품질은 빌트인
   `/code-review`에 위임한다. **차단이 남으면 Phase 3으로 되돌린다** — 담당을 같은 이름으로
   깨운다. 게이트가 마커를 찍지 않으면 다음 단계의 PR 생성 명령이 훅에 막힌다.

   린트가 통과했다는 것은 이 리뷰의 **입력이지 결론이 아니다.** 이 저장소의
   검증 도구는 통과 신호를 여러 번 위조했고 전부 린트·프리뷰가 초록불이었다(횟수와 목록은 docs/HARNESS.md 「핵심 위험」이 정본).
6. **푸시 → PR 생성.** 사이클의 기본 종료 지점이다 (merge는 하지 않는다). 마커 기록·푸시·PR 생성은 **각각 다른 Bash 호출**로 낸다 — 게이트 훅은 PR 생성이 든 호출에 다른 명령이 있으면 막는다(이슈 #111).
   PR 본문에 **무엇을 / 왜(`DECISIONS.md`·`DESIGN.md` 참조) / 어떻게 확인했는가 / 검증하지 못한 것**을 담는다.
   QA 리포트와 리뷰의 "미검증"·"경고" 항목을 PR에 그대로 옮긴다 — 리뷰어가 알아야 한다
7. **피드백 요청** — "결과에서 고치고 싶은 부분이 있나요? 팀 구성이나 순서에 바꿀 점이 있나요?"

## 에러 핸들링

| 상황 | 전략 |
|---|---|
| 팀원이 응답하지 않는다 | 긴 턴 중이면 답이 턴 끝에 온다 — 마지막 지시 뒤에 유휴 알림이 아직 안 왔으면 일하는 중이니 기다린다(`ListAgents`는 팀원을 보여 주지 않는다). 유휴 알림이 왔는데 상태 확인에 답이 없거나 오류로 끝났을 때만 `TaskStop`으로 멈추고 같은 정의를 **같은 이름**으로 다시 띄운다. 이전 산출물 경로와 작업표의 해당 줄을 프롬프트에 넣는다. 새 이름을 쓰지 않는다 — 다른 팀원이 옛 이름으로 보내면 멈춘 쪽이 맥락째 깨어나 새 쪽과 같은 파일을 고친다. 같은 이름이면 메시지가 새 쪽으로 간다(실측). 재실패 시 해당 작업을 리더가 직접 수행하고 리포트에 명시 |
| 팀원으로 뜨지 않는다 (환경 차이) | `Agent(name:)` 결과가 「mailbox로 지시를 받는다」가 아니라 일반 비동기 실행이면 팀원이 아니다. 문구는 판마다 바뀔 수 있으니 애매하면 짧은 메시지를 보내 유휴 알림이 오는지로 가린다(플래그가 꺼졌거나 백그라운드 잡 — 2026-08-26에 백그라운드 잡에서는 팀 도구가 안 올라왔다). 사용자에게 한 줄로 알린다. 흐름은 같다 — 체크포인트마다 skin-qa를, 고칠 때마다 생산 팀원을 새로 띄우고 이전 산출물 경로를 넘긴다. 맥락은 잃지만 체크포인트는 리더가 쥐고 있으므로 검증이 빠지지 않는다 |
| 팀원이 "통보할 수단이 없다"고 보고 | `SendMessage`가 지연 도구라는 것을 몰랐다. 프롬프트에 불러오는 법을 넣었는지 확인한다. 정말 못 쓰는 환경이면 최종 보고 → **리더가 중계**한다 |
| 훅 계약 충돌 반복 | 리더가 개입해 이름을 확정하고 양쪽에 통보. 팀원 협상에 맡기지 않는다 |
| 체크포인트 실패가 3회 반복해도 안 잡힘 | 사용자에게 보고하고 진행 여부 확인. 억지로 통과시키지 않는다 |
| 리뷰 게이트가 차단 판정 | Phase 3으로 되돌려 고치고 **게이트를 다시 실행**한다. 마커를 손으로 찍지 않는다 — 찍는 순간 초록불이 거짓이 되고, 다음 사람이 그것을 믿는다 |
| PR 생성이 훅에 막힘 | 리뷰를 안 했거나, 리뷰 뒤 커밋이 쌓였거나, **마커 기록과 PR 생성을 한 명령에 묶었다.** `/pr-review-gate` 「게이트 오작동 흐름」을 따른다 — 리뷰가 **지금 HEAD를 보고 차단 0으로** 끝났을 때만 마커를 따로 찍고, 막혔던 명령의 나머지(푸시 포함)를 다시 낸다 |
| 프리뷰가 렌더링 안 됨 | **스킨이 아니라 렌더러 문제일 수 있다.** 경고를 먼저 읽고, 렌더러 결함이면 리더가 `.claude/skills/skin-preview/scripts/render.py`를 고친다 — 팀원이 모두 유휴일 때 |
| 치환자가 필요한데 없음 | 지어내지 않는다. `docs/tistory-skin-reference.txt` 확인 후, 없으면 JS 구현으로 우회하거나 사용자에게 보고 |
| `DESIGN.md`에 없는 값 필요 | 임의 결정 금지. 문서를 먼저 갱신하고 사용자에게 알린다 |

## 테스트 시나리오

### 정상 흐름
1. 사용자: "홈 화면부터 만들어줘"
2. Phase 0 — `_workspace/` 없음 → 초기 실행
3. Phase 1 — `data/posts.json`이 최신이라 건너뜀
4. Phase 2 — 작업 15개를 `_workspace/tasks.md`에, 기준선 오류 0
5. Phase 3 — markup이 작업 1 → 리더가 이름을 복사해 style·behavior를 띄우고 markup을 깨워 3~5 →
   behavior의 작업 10은 markup의 작업 5 보고 뒤에 → 모두 유휴 → 1차·2차 체크포인트, 경계면 이슈 1건은
   qa가 검증을 마친 뒤 style·behavior 양쪽에 → 같은 이름으로 고침
6. Phase 4 — 마지막 체크포인트: 린트 오류 2건 → 담당을 같은 이름으로 깨워 고침 → 다시 체크포인트 → `npm run check` 통과 · 다크모드 확인
7. Phase 5 — 팀원 `TaskStop` → 커밋 → `/pr-review-gate` 경고 1·차단 0 → 마커 → (별도 명령으로) 푸시 → PR
8. 예상 결과: `dist/skin.html` · `dist/style.css` · `dist/images/script.js` 생성, 프리뷰 12페이지 정상

### 에러 흐름
1. Phase 3에서 `skin-behavior`가 응답 없음
