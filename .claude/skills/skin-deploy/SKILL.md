# 배포 — 수동 절차

**이 프로젝트는 비공식 API를 쓰지 않는다**(`DECISIONS.md` #15). 배포는 사용자가 티스토리 스킨 편집기에서 직접 한다. Claude의 역할은 **붙여넣을 것을 정확히 준비하고, 순서를 안내하고, 되돌릴 수 있게 만드는 것**이다.

## 배포 전 필수

```bash
npm run build
python3 .claude/skills/skin-qa-check/scripts/lint.py    # 오류 0이어야 한다 (SEO001~002 포함)
python3 .claude/skills/skin-preview/scripts/render.py   # 11개 페이지 육안 확인

# 배포 전 라이브 상태를 기준선으로 남긴다. 배포 후 회귀 비교의 근거가 된다.
python3 .claude/skills/seo-verify-live/scripts/verify.py --base https://<블로그> --save-baseline
```

**네 명령을 같은 체크아웃에서 돌린다.** `dist/`는 `.gitignore`라 체크아웃 밖으로 나가지 않는다. 빌드한 곳이 아닌 데서 검증하면 `V009`가 "`dist/style.css`가 없다"로 미검증이 되어, **배포한 CSS가 방금 빌드한 것인지 확인하지 못한 채** 넘어간다. baseline도 마찬가지다 — `data/seo-baseline.json`은 git으로 공유되므로 커밋하지 않으면 배포 후 `--compare`가 다른 체크아웃에서 보이지 않는다.

**린트 오류가 남아 있으면 배포하지 않는다.** 이 도메인의 오류는 조용히 실패하므로, 배포 후에는 발견이 늦다.

**baseline을 먼저 찍는 이유** — 배포 후 "내부링크가 줄었다"를 알려면 배포 전 값이 있어야 한다. 이 단계를 건너뛰면 배포 사고를 절대값으로만 판단하게 되고, 그러면 대부분 놓친다.

⚠️ **`--save-baseline`은 오류를 내고 exit 1로 끝나는 것이 정상이다.** 이 시점의 라이브는 아직 **이전 스킨**이라 `V009`(라이브 CSS ≠ `dist/style.css`)는 반드시 뜨고, `V003`·`V010`도 이전 스킨의 상태를 그대로 보고한다. 위의 "린트 오류가 남아 있으면 배포하지 않는다"는 `lint.py`에 대한 말이지 이 명령에 대한 말이 아니다 — 여기서 멈추지 마라.

**딱 하나 예외는 `V014`다.** 이게 뜨면 baseline이 **저장되지 않았다** — 페이지를 못 받았다는 뜻이다. 그대로 배포하면 배포 후 `--compare`가 비교할 것이 없어 회귀를 못 잡는다. 원인을 고치고 baseline부터 다시 찍어라.

검증기는 `--base`가 `data/posts.json`의 블로그와 다르면 **대상 블로그에서 글·카테고리를 직접 찾는다.** 못 찾으면 `V000`이 뜨고 `--post-path`·`--category`로 지정할 수 있다 (`/seo-verify-live`). 한번 baseline이 찍히면 그 대상이 고정되어, 배포 전과 후가 **같은 글**을 비교한다.

## 첫 배포 — 백업이 먼저다

현재 라이브 스킨을 되돌릴 수 있어야 한다. 사용자에게 다음을 요청한다:

1. **티스토리 관리 → 꾸미기 → 스킨 편집 → html 편집**에서 현재 `skin.html`·`style.css` 전문을 복사해 `backup/hello-skin.html`, `backup/hello-style.css`로 저장
2. **파일업로드 탭**의 파일 목록을 캡처하거나 이름을 받아 적어 `backup/files.txt`로 저장
3. **스킨 보관함에 현재 스킨 저장** — 관리 → 꾸미기 → 스킨 편집 → "스킨 저장". 가장 확실한 되돌리기 수단이다

## 배포 순서

순서가 중요하다. **`index.xml`을 마지막에 올린다.**

| 순서 | 대상 | 위치 | 주의 |
|---|---|---|---|
| 1 | `dist/images/script.js` | 스킨 편집 → **파일업로드** | 기존 동명 파일이 있으면 먼저 삭제 |
| 1-b | `dist/preview.gif` · `preview256.jpg` · `preview560.jpg` · `preview1600.jpg` | 스킨 편집 → **파일업로드** | 바뀌었을 때만. 이름 덕에 스킨 **루트**로 간다 |
| 1-c | `dist/images/ph-<slug>-<theme>.v<N>.webp` **30장** | 스킨 편집 → **파일업로드** | **기본 이미지가 바뀐 배포에서만** (결정 5·6 개정). 반드시 **style.css보다 먼저** — 반대면 그 사이 카드가 점격자만 남는다. 버전(N)이 올랐으면 새 이름으로 올리고 옛 버전 30장은 지운다. **처음 올릴 때 개수·용량 거부가 나는지 기록한다**(미결 1) |
| 2 | `dist/style.css` | 스킨 편집 → **CSS** 탭 | 전체 선택 후 덮어쓰기 |
| 3 | `dist/skin.html` | 스킨 편집 → **HTML** 탭 | 전체 선택 후 덮어쓰기 |
| 4 | `dist/index.xml` | 스킨 편집 → **index.xml** | ⚠️ **스킨의 모든 설정이 초기화된다** |
| 5 | 저장 후 **미리보기**로 확인 | | 적용 전 마지막 관문 |
| 6 | 적용 | | |

### 미리보기 이미지도 파일업로드 탭으로 올린다

`preview.gif` · `preview256.jpg` · `preview560.jpg` · `preview1600.jpg`는 스킨 **루트**에
있어야 한다(`docs/tistory-skin-reference.txt:51`). 없으면 관리 화면의 "사용중인 스킨"과
스킨 보관함에 **깨진 이미지가 뜬다.**

**파일업로드 탭이 이 이름들을 루트로 보낸다.** 목적지가 파일명으로 갈린다 —
2026-08-25 실측:

| 올린 파일 | 실제 위치 |
|---|---|
| `script.js` | `…/skin/images/script.js` |
| `preview.gif` · `preview256.jpg` · `preview560.jpg` · `preview1600.jpg` | `…/skin/` **루트** |

⚠️ **zip 업로드는 받지 않는다.** 스킨 보관함의 "직접 업로드"로 스킨 패키지를 올리는
경로는 이 블로그에서 동작하지 않았다(2026-08-25 실측). 배포는 편집기 붙여넣기 +
파일업로드뿐이다.

확인은 URL을 직접 두드리는 게 가장 빠르다. 스킨 루트는 라이브 HTML의 `style.css`
주소에서 얻는다:

```bash
curl -sS -o /dev/null -w "%{http_code}\n" \
  https://tistory1.daumcdn.net/tistory/<블로그번호>/skin/preview256.jpg
```

미리보기 이미지를 다시 만들려면:

```bash
npm run preview:images    # macOS + Chrome 필요
```

### `index.xml`이 마지막인 이유

이 파일을 바꾸면 스킨 설정이 초기화된다. 먼저 올리면 이후 작업 중에 사용자가 설정을 다시 맞춰야 하고, 그 사이 라이브 화면이 어중간한 상태가 된다. **바꿀 내용이 없으면 아예 올리지 않는다.**

## 배포 후 확인

라이브에서 직접 확인해야 하는 것들 — **로컬 프리뷰가 원리적으로 재현하지 못하는 영역이다.**
치환자·고정 마크업은 조용히 실패하므로, 아래를 안 보면 "잘 나온다"와 "안 나온다"를 구분할 수 없다.

### 1. 먼저 스크립트를 돌린다

```bash
python3 .claude/skills/seo-verify-live/scripts/verify.py --base https://<블로그> --compare
```

**소스가 맞아도 프로덕션이 틀릴 수 있다.** 붙여넣다 잘린 마크업, 안 올라간 `script.js`, 반영 안 된 CSS는 배포 전 린트가 절대 잡지 못한다. 이 스크립트가 잡는 것: 미치환 치환자 잔존, `h1` 개수, 내부링크 렌더 여부, 라이브 CSS ↔ `dist/style.css` 대조, 8개 페이지 응답, baseline 대비 회귀. 자세한 것은 `/seo-verify-live`.

`V010`(모바일웹 자동 연결)이 뜨면 **코드로 못 고친다** — 아래 모바일웹 OFF 항목을 보라.

### 2. 카테고리 트리가 **리스트형**으로 나오는가

2026-08-25 첫 배포에서 폴더형(`[##_category_##]`)이 나갔다. 중첩 `<table>`과 트리선 GIF로 된
티스토리 기본 트리가 그대로 노출됐고, 우리 CSS는 한 줄도 매칭되지 않았다 (`DECISIONS.md` 결정 31).
지금은 린트 `CAT001`이 막지만, **배포는 손으로 하는 복붙이라 소스가 맞아도 프로덕션이 틀릴 수 있다.**

- [ ] 사이드바 트리에 **`├` `└` 모양의 트리선 이미지가 없는가.** 있으면 폴더형이다
- [ ] 개발자도구에서 `ul.tt_category`가 있는가 (`<table id="treeComponent">`이면 폴더형)
- [ ] 카테고리 링크를 **키보드 Tab으로 지나갈 수 있는가.** 폴더형은 `onclick`이라 닿지 않는다
- [ ] 현재 보고 있는 카테고리에 왼쪽 파란 막대(`li.selected`)가 표시되는가
- [ ] **다크로 전환** → 트리가 읽히는가. 리스트형은 인라인 색이 없어 정상이어야 한다.
      글자가 흐리거나 흰 박스가 뜨면 **폴더형이 나간 것이다** (`DECISIONS.md` 결정 31)
- [ ] 240px 레일에서 긴 이름(`성능과 동시성` · `Django·Flask`)이 줄바꿈되지 않는가.
      로컬 계측으로는 안 났지만 실제 폰트 렌더가 다를 수 있다

### 3. 페이지 · 영역이 실제로 나오는가

- [ ] 홈 · 글 · 카테고리 · 검색 · 태그 · 보관함 · 방명록 각 URL
- [ ] **공지** (`<s_notice_rep>`) — 홈 상단에 공지 전문이 깔리는가, 아니면 퍼머링크에서만 나오는가.
      **테스트 블로그에 공지가 0건이라 2026-08-25 배포에서도 확인하지 못했다.** 공지를 하나
      만들고 봐야 한다 — 전문이 깔리면 모바일 첫 화면을 공지가 다 먹는다
- [ ] **홈의 카드 그리드** — `<s_list>`가 홈에서도 렌더된다(결정 29). 홈은 3열 그리드,
      목록 4종은 세로 행이다. 같은 마크업이라 body_id 게이트가 빠지면 홈 카드에 밑줄이
      깔리고 썸네일이 180px로 눌린다
- [ ] 🔴 **글 페이지에 `.entry-title`·`.entry-body`가 있는가.** 없으면 `<s_permalink_article_rep>`가
      `<s_article_rep>` 밖으로 나간 것이다 — 티스토리가 통째로 버리고 **에러를 내지 않는다**.
      2026-08-25에 실제로 겪었고, 그때 홈은 멀쩡해 보였다. 린트 `SUB008`이 먼저 잡아야 한다
- [ ] **`/tag`와 `/tag/이름`에서 h1이 하나씩인가.** 둘 다 `tt-body-tag`인데 `/tag`는 클라우드
      (`.tagcloud-title`), `/tag/이름`은 목록(`.list-title`)이고 **둘 다 h1**이다. 티스토리가
      한 URL에서 두 영역을 함께 렌더하면 h1이 두 개가 된다. 그러면 `.tagcloud-title`을 h2로 내린다
- [ ] **페이지마다 h1이 하나인가** — 글·목록·클라우드·방명록은 각자의 영역이 h1을 갖는다.
      **홈도 마찬가지다** — `.list-title`이 "전체 글"로 채워진다(결정 29). 헤더의 블로그 이름은
      h1이 아니다. 거기에 h1을 두면 다른 페이지에서 반드시 둘이 된다
- [ ] **헤더의 검색 상자** — 공식 예시는 사이드바다. 헤더에서 `<s_search>`가 죽으면 통째로 사라진다
- [ ] **글 상단 "댓글 N" 링크** — `<s_rp_count>`가 `<s_permalink_article_rep>` 안에서 렌더되는가
- [ ] 사이드바 **공지 모듈**(`<s_rct_notice>`)
- [ ] **보호글** 화면

### 4. 티스토리가 통짜로 렌더하는 것

- [ ] **댓글 UI** — React 출력. `tistory.css`의 `tt-*` 클래스 이름이 실제와 맞는지. 틀리면 무스타일로 나온다
- [x] ~~**카테고리 트리 클래스**~~ — 2026-08-25 확정. 리스트형은 `중첩 ul을 가진 li` 구조가 맞다
      (`ul.tt_category > li > ul.category_list > li > ul.sub_category_list`). 위 2번에서 함께 본다
- [ ] **페이징 현재 페이지** — 티스토리가 붙이는 클래스 이름을 **모른다.** 대응 CSS가 아예 없다.
      확인한 이름을 `components.css`에 추가할 것
- [ ] **페이징 `no_more_prev` / `no_more_next`** — 갈 곳 없는 화살표가 흐려지는가
- [ ] **목록 카드의 "댓글 0"** — 홈 카드는 `<s_rp_count>`로 감쌌지만 목록 카드는 안 감쌌다.
      `<s_rp_count>`가 `<s_list_rep>` 안에서 동작한다는 근거가 문서에 없어서다.
      "댓글 0"이 실제로 남으면 그때 감싸고 목록 4종을 다시 본다
- [ ] **`.list-desc`** — 검색·태그·보관함에서 비는가. 안 비면 "카테고리 설명"이 검색 결과 위에 남는다

### 5. 다크모드 — 여섯 상태

`data-theme` 3상태 × OS 2상태다. **저장된 선택이 없는 첫 방문자**가 기본값이므로 그것부터 본다.

- [ ] stamp 없음 + OS 다크 / OS 라이트 (localStorage를 비우고 확인)
- [ ] `data-theme="dark"` + OS 라이트 / `data-theme="light"` + OS 다크 (교차 상태에서 명시가 이겨야 한다)
- [ ] **본문 인라인색** — 옛 글(2018~2020)의 `style="color: #000000"`이 다크에서 읽히는가
- [ ] JS를 끄고 한 번 — `inline-fix.js` 없이 CSS만으로 보정되는지

**티스토리 에디터 컴포넌트** — 인라인색과 **원리가 다른** 별도 항목이다(DESIGN.md §5.2b).
색이 `style` 속성이 아니라 티스토리 스타일시트에 있어 인라인 보정이 원리적으로 못 잡는다.
프리뷰에서 통과해도 라이브에서 다시 본다 — 티스토리가 시트를 언제든 바꿀 수 있기 때문이다.

- [ ] **오픈그래프 링크 카드** — 카드 **제목**이 보이는가. 실측 62곳 / 39편으로 가장 흔하고 가장 심했다(1.00:1)
- [ ] **인용문** — `style1`(글머리 큰따옴표)과 `style3`·`box`(테두리 상자). 상자가 **흰색으로 뜨지 않는가**
- [ ] **인용문 안 문단** — `<p>`가 본문색을 물려받는가 (직접 지정이 상속을 이기는 자리다)
- [ ] **표** — `data-ke-style` 표의 줄무늬·첫 열이 밝은 회색으로 뜨지 않는가
- [ ] **코드블록 구문 색** — 키워드·숫자가 우리 팔레트 색인가. 보라(`#a626a4`)·갈색(`#986801`)이 보이면
      `atom-one-light`이 이긴 것이다 → `.hljs ` 접두 확인
- [ ] **"카테고리의 다른 글" 상자** — 제목과 링크가 읽히는가 (`!important` 싸움)

## 되돌리기

문제가 생기면 **스킨 보관함에서 이전 스킨을 다시 적용**한다. 그것이 가장 빠르다. `backup/`의 HTML·CSS를 붙여넣는 것은 차선책이다(업로드 파일은 복구되지 않는다).

기본값으로 떨어지는데 **에러는 나지 않는다.** `data/categories.json`을 그 블로그 기준으로 갱신하고
린트 `BND003`으로 빠진 것을 확인한다.
